AODV is not silent when idle by default: it sends a HELLO every second. That matters for the sustained-phase (battery) half of the premise.

## AODV without hellos can't detect a dead next hop at the source

AODV's link-layer feedback (`Neighbors::ProcessTxError` in `src/aodv/model/aodv-neighbor.cc`) only acts on nodes already in AODV's neighbour table. Hellos add neighbours to that table. Forwarding also adds them, but only at intermediate and destination nodes (`RouteInput`), never at the node that originates the traffic.

So with `EnableHello=false`, the sending node never learns that its first hop died, and the route never recovers. In the diamond sim, `--aodvHello=false` shows this. Turning AODV hellos off is therefore not a fair configuration for the comparison in NS-3.47. The comparison has to be AODV with hellos vs OLSR, or the paper has to explain and justify any change.

## Link-break detection differs between the three protocols

- **AODV** hooks the MAC's `DroppedMpdu` trace (`aodv-routing-protocol.cc`), so a unicast frame that reaches the retry limit tells AODV the next hop is gone. It also notices missing HELLOs after `AllowedHelloLoss` × `HelloInterval`.
- **OLSR** has no MAC feedback. It notices a dead neighbour only when HELLOs stop for the neighbour hold time (6 s), and the rest of the network learns through TC messages.
- **DSDV** has no MAC feedback either. A route is dropped only after 45 s without an update (Holdtimes × PeriodicUpdateInterval).

So an idle radio draws 0.273 A × 3 V = 0.82 W whether or not it is routing anything. Sending and receiving add only 0.04–0.11 A on top. In this model, idle listening dominates a node's energy use, which limits how much routing traffic alone can change battery life (relevant to the sustained-phase half of the premise).

## Simulation artifacts handled in the code

- **ARP collisions.** In a perfectly symmetric topology, B and D answer A's first route request at the same instant, and their ARP lookups collide every time. Both sims pre-fill every ARP table with PERMANENT entries to remove this. State it in the methods section.
- **Don't use `NeighborCacheHelper` with AODV.** It was used at first, but its entries are `STATIC_AUTOGENERATED`, and AODV's `Neighbors::LookupMacAddress` (`src/aodv/model/aodv-neighbor.cc`) only accepts entries that are `ALIVE` or `PERMANENT`. With it, AODV's MAC-based link-break detection never fires, and a relay that keeps forwarding into a dead link keeps its route alive and becomes a black hole. Both sims now add PERMANENT entries by hand. (Found on 27 Oct 2026. AODV results from before this fix were produced without MAC-based link-break detection; rerun them.)
- **Switching a radio off mid-frame can crash ns-3.47.** For a frame that needs no acknowledgement (any broadcast, such as a routing HELLO), `FrameExchangeManager::SendMpdu` schedules `TransmissionSucceeded()` for the end of the transmission. `WifiPhy::SetOffMode()` calls `FrameExchangeManager::Reset()`, which sets `m_dcf` to null but doesn't cancel that event, so `TransmissionSucceeded()` then dereferences a null pointer (`src/wifi/model/frame-exchange-manager.cc`). `sim/manet` therefore lets a radio finish the frame it is sending before switching it off (at most a few milliseconds).
- **Range model.** The diamond sim uses `RangePropagationLossModel` (hard 110 m cut-off) so the topology is exact. Within range the received power equals the transmit power; beyond it, -1000 dBm (`propagation-loss-model.cc`). `sim/manet` uses the same model with a 150 m range. The Kerala scenario needs a realistic propagation model (open question 11).
- **Killing a node.** `WifiPhy::SetOffMode()` switches the radio off, so the node stops sending, receiving and acknowledging frames, like a dead battery. Taking only the IP interface down would leave the MAC still acknowledging frames, which isn't how a dead device behaves.
